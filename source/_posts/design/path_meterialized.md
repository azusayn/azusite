## 1. 需求

利用树形结构的场景包括：

- 组织架构 （集团总部 > 华东大区 > 上海分公司 > 研发中心 > 基础架构部 > 中间件组）
- 空间层级 （南山科技园 > A栋创新大厦 > 22层办公区 > 南侧核心机房 > 动环监控与出入口综合布防点）

设计这样的层级我认为主要有这些因素：

- 人脑记忆的习惯，这样做省脑子
- 按照树状去组织结构对于需要继承的特性来说十分便利（比如权限）
- 底层节点的状态可以不断聚合到最上层（冒泡），便于管理

围绕着这样的树状结构的存储和检索，我们考虑这些问题：

- 渲染树形结构并显示。用户可能对任意节点拥有权限，同时对于所在节点往上到根节点中间的所有节点都至少有读权限（为了简化问题，接下来我们只考虑读权限）
- 在树中任意位置插入节点
- 删除一个节点（可能会引发子节点的删除）
- 根据节点路径插入节点（比如利用别的系统来的文件批量插入节点）
- 用户可以随意的地调整任何节点，插入到新的位置（节点下的子节点会被一起移动）

这个文档主要对比邻接表 (Adjecency List) 和物化路径 （Materialized Path）两种组织方式的性能差异（§2.1），将其他关键设计放在（§2.2）进行讨论。并在最后附上性能测试
（§3）以及一些额外的思考

## 2. 系统设计

### 2.1 两种节点层级的表示方式

#### 2.1.1 邻接表 （Adjacency List）- 使用 Parent ID

在我们这个背景下，我们存储的是一颗多叉树，由于我们需要从某个节点向上找到父节点，所以每一个节点的数据库行在内存里可以表示为:

```go
    // 很遗憾数据库里面没有 Node* parent
    type Node struct {
        ID       int
        ParentID int
        // 按照系统这个字段既是功能也能作为唯一标识符的一部份
        Name     string
    }
```

> 接下来的讨论都基于 “同层节点不能存在同名称的节点” 的规则

但是这个表示方式会带来一些麻烦。具体体现在：

- 查询用户所在节点到根节点的中间节点需要递归查询（程序里面递归或者数据库 CTE）

- 用户按照名称路径批量插入数据的时候，为了确认新节点的直接父节点，我们需要先查询出直接父节点的 ID。我们需要通过完整的路径才能确定父节点的唯一位置，因为不同层下面可能会存在相同名称的节点。这无法通过简单的查询完成。

- 业务上需要在添加新节点的时候做层级限制，我们只能通过递归查询的方式来判断层数

- 若要删除某个非叶节点，需要递归查询 `WHERE parent_id = xxx`

#### 2.1.2 使用物化路径（Materialized Path）

我们可以将节点表示为

```go
    type Node struct {
        // "/A/B/C"
        // 规定一个 dummy 根节点
        Path string
    }
```

- 对于查询用户所在节点到根节点的完整路径，只需要简单的根据 Path 的 "/" 分隔符进行切分，在数据库中查询所有匹配的 Path 即可。

- 批量插入名称路径的时候，利用字符串规律将所有可能子路径直接插入数据库。利用 `INSERT IGNORE` （MySQL）或者 `INSERT ON CONFLICT DO NOTHING`（Postgres） 等数据库特性防重复。

- 为了判断某个节点层数以进行业务限制，直接利用 Path 进行判断。

- 删除某个非叶节点只需要 `WHERE path LIKE '/xxx%'. 这里因为 path 左侧有一段没有通配符，所以可以利用索引

> 为了查询效率，我们会在 Path 上建立唯一索引，但对于字符串值建立索引而言有长度限制。
>
> - [Postgres](https://www.postgresql.org/docs/current/btree.html#:~:text=PostgreSQL%20includes%20an%20implementation%20of%20the%20standard,a%20page%20(after%20TOAST%20compression%2C%20if%20applicable).) 最大索引长度 2704 个字节
> - [MySQL](https://dev.mysql.com/doc/refman/8.4/en/innodb-limits.html#:~:text=This%20section%20describes%20limits%20for%20InnoDB%20tables%2C,transactions%2C%20see%20Section%2017.6.%206%2C%20%E2%80%9CUndo%20Logs%E2%80%9D.) 最大索引长度 3072 个字节
>
> 如果超出长度限制则需要额外方法：在 MySQL 中可以使用前缀索引，在 Postgres 中可以将 path 进行 hash
>

### 2.2 其他核心功能设计

#### 2.2.1 节点排序与存储

在界面上，用户可以拖动节点放到树的任何一个位置，对于后端来说，拿到的数据是被拖动的节点的新位置的父节点，以及在哪个节点之前（后）。

同层节点有一定顺序，并且为了保证用户没有权限的时候，节点还能正常显示，节点之间不能像是 B+ 树一样用指针连在一起。所以我们可以给节点安排一个排序号，或者说权重 (Weight)。

如果只是从 1 开始安排排序号，同层节点发生位置变化或者插入的时候，大概率会触发同层节点排序号的重新赋值。

所以这里使用稀疏权重的设计，在一个 int64 范围内安排同层排序权重，假设我们需要在两个节点间插入新节点，我们只需要用两个节点的权重平均值作为新节点的权重，直接将新节点数据插入数据库即可。这样只会有极小的概率会引发同层节点重排（即两个节点之间的距离小于 2）。

<img src="/images/path_materialized/sparse_weights.svg" alt="sparse_weights" style="zoom: 50%;" />

稀疏权重的设计有效避免了处理并发问题的麻烦，假如我们是把数据从数据库读到内存重新排序，我们就需要应用层内部的锁，如果是多实例部署，我们需要引入分布式锁或者 Postgres 的 Advisory Lock 那样的东西。而稀疏权重下，绝大部分情况下我们只对单行数据进行更新（数据库自己会处理好单行锁的原子性！）。

#### 2.2.2 渲染嵌套数据

假如我们已经有一组 Node 节点数组 nodes，为了便于前端进行渲染（~~让前端偷懒少写点代码~~），我们需要将数据组织为嵌套的 JSON 结构
返回给前端。思路大致如下：

1. 定义一个新的结构体用于表示嵌套结构：

    ```go
    type MemNode struct {
            Path    string
            Childs []*MemNode
        }   
    ```

2. 遍历 nodes， 对于每一个节点都可以根据 Path 字段确定它的直接父节点。将自身添加到直接父节点的 Childs 数组中

对于使用 ParentID 来标识父节点的方案，在渲染步骤比 Path 方案少了一步 —— 根据 Path 确定 Parent Path 需要额外的计算。不过这个损耗可以忽略不计。所以在渲染阶段这两个方案性能没有太大差别。

## 3. 两个场景的性能测试

常使用的接口是展示、排序、导入、删除，下面使用 Go 标准 testing 构建测试。由于官方的 pprof block 主要记录的是 Go 并发原语造成的阻塞调用（锁竞争或堵在 Channel 上），无法显示网络或者磁盘 IO 带来的问题。

下面利用 fgprof 工具分别生成新旧实现的火焰图，它会基于 Wall Clock 进行采样，图上占用 samples 多的调用就能说明花费的真实时间长（采样率保持一定的情况下）。接着使用两张图生成差分火焰图。另外也会使用 Go 的 runtime/trace 生成 Network Blocking Profile （相当于 RTT + 数据库内部 IO）。

考虑到真实情况下，不同场景的数据分布不一样（瘦/胖树、高/矮树），对数据结构的操作需求也不同（读多/写多）。所以下面会用两个不同的场景进行测试分析

### 3.1 组织架构

以公司或学校等组织架构为例（如：集团总部 > 华东大区 > 上海分公司 > 研发中心 > 基础架构部 > 中间件组）。这种场景表现为树的层级较深（大概 6 到 10 层左右），但同层节点并不会太多（大概 5 到 20 个，比如一个研发部门下面设立 5 到 20 个左右的具体技术团队）。

这里采用了 7 层深度，从顶层开始每一层的 fanout 配置分别为 [2, 3, 3, 4, 4, 15]，总规模约 4000+ 节点。得到测试结果如下：

| 接口与场景 | 原逻辑 (ms) | 现逻辑 (ms) | 性能比 (原/现) |
| --- | --- | --- | --- |
| **Tree / 三角色平均** | 12.11 | 23.33 | 0.52x |
| **Sort / 同层随机** | 6.38 | 2.51 | **2.54x** |
| **Sort / 混合随机** | 6.73 | 2.86 | **2.36x** |
| **Import / 批量导入** | 27.48 | 6.76 | **4.06x** |
| **Delete / 子树删除** | 2.96 | 2.74 | 1.08x |

可以看到除了 Tree 接口性能变差以外，接口性能都有了较大的提升。

#### 3.1.1 Tree 接口分析

对于 Tree 而言，在拿到所有有权限的组织 ID 后，会进行 `WHERE IN` 查询，物化路径实现是在字符串集中进行匹配，邻接表实现是在 INT64 中匹配。针对 Tree 的实现，生成差分火焰图与 Network Blocking Profile，其中 `FindAllByPaths` 和 `Array` 分别是字符串和 INT64 匹配的那两个 SQL。

- 两张火焰图进行差分：
    <img src="/images/path_materialized/mp_dl_flamegraph.png" alt="mp_dl_flamegraph.png" style="zoom: 80%;" />

- Go runtime/trace 的 Network Blocking Profile （新实现）：

    <img src="/images/path_materialized/network_blocking_profile.png" alt="network_blocking_profile" style="zoom: 80%;" />

分析两张图可以看出多的开销主要来自 `FindAllByPaths` 和 `ExtractPathHierachy` （构造查询用的 path） 这两个调用。具体来说，性能变差是因为：

- 字符串通常占据更多空间，导致一个 B+ 树非叶节点能存入的索引键就更少，导致更高的树，更多的跳转。由于叶节点存储的字符串有限，页分裂后，更容易出现随机 I/O 。
- 字符串对缓存行不友好，变长的字符串过小或者过大都会导致跨行读取。另一方面，大字符串会导致 cache line 里面能放的有效数据减少。对于 B+ 树的热数据，它们可能会被别的大字符串挤出缓存。
- 字符串键的索引匹配本身没法像是数值键那样一个 CPU 指令就能完成，需要更多的操作次数。

不过这里引入一个新的假设，拥有比较下层组织权限的角色，一般只是继承子组织的权限，所以比较于上层节点他们前一步 `ExtractPathHierachy` 构造查询路径的步骤，会得到更少的输入，`FindAllByPaths` 的开销相应就会减少，不使用递归的优势就会凸显出来。所以针对拥有不同高度节点权限的角色，分别进行了测试，得到新的结果：

| 接口与场景 | 原逻辑 (ms) | 现逻辑 (ms) | 性能比 (原/现) |
| --- | --- | --- | --- |
| **Tree / 三角色平均** | 12.11 | 23.33 | 0.52x |
| **Tree / 上层角色** | 30.84 | 66.32 | 0.46x |
| **Tree / 中层角色** | 3.08 | 2.64 | 1.17x |
| **Tree / 下层角色** | 2.41 | 1.03 | **2.34x** |

没错！这个优化的精髓就在于这个系统除了 Boss 用起来有点糟心以外，其他人都感觉更舒适了（

至于这点高层们可以付费开通 VIP 缓存通道。

#### 3.1.2 Sort 接口分析

在 Sort 接口里，用户可以操作节点在同层之间移动，或者拖动到不同父节点下面。由于考虑这个功能大部份时间都是同层操作（应该不会有人频繁更换部门调岗）。所以针对同层随机单独进行了测试。它的性能提升比混合测试条件下要多，因为将节点拖动到新的父节点下面涉及所有子节点 path 的 `UPDATE`。不过对比起递归找子节点的邻接表实现，他的性能还是达到了 2-3X。

#### 3.1.3 Import 接口分析

批量导入的时候，领接表实现需要对每一个路径先查出直接父节点的 `id` 用于更新 `parent_id`，而物化路径只需要简单的插入即可。而且邻接表为了避免并发问题，还可能需要 `SELECT FOR UPDATE` 或者分布式锁。

#### 3.1.4 Delete 接口分析

两个实现测试结果差别并不是很大，因为测试的时候选择的是小规模的子树删除（考虑到很少会直接删除比较上层的组织节点） 。邻接表的实现递归查询子节点的劣势并没有体现出来。而物化路径实现使用的 `LIKE XX%` 也没有造成明显劣势，甚至略快。

### 3.2 空间层级

以物理空间或安防物联网系统为例（如：南山科技园 > A栋创新大厦 > 22层办公区）。这种场景下主要是层级相对较浅（大概 5 到 10 层），但同层节点较多（大概几十到上千个不等，比如单栋大楼往往有几十层、每层有数十个房间，这些房间关联上数十个 IoT 传感器、摄像头等）。

这里采用了 6 层浅而宽的树形分布，从顶层到底层的 fanout 配置分别为 [2, 5, 10, 5, 18]，总规模约 9000+ 节点。得到测试结果如下：

| 接口与场景 | 原逻辑 (ms) | 现逻辑 (ms) | 性能比 (原/现) |
| --- | --- | --- | --- |
| **Tree / 大分区角色 (large)** | 39.56 | 119.06 | 0.33x |
| **Tree / 中层角色 (mid)** | 12.54 | 22.11 | 0.57x |
| **Tree / 叶子角色 (leaf)** | 2.66 | 1.10 | **2.42x** |
| **Tree / 三角色平均** | 18.25 | 47.42 | 0.38x |
| **Sort / 同层随机** | 21.66 | 8.11 | **2.67x** |
| **Sort / 混合随机** | 25.09 | 9.85 | **2.55x** |
| **Import / 小区 CSV 导入** | 15396.25 | 683.40 | **22.53x** |
| **Delete / 子树删除** | 186.60 | 140.42 | **1.33x** |

基本上得出的结论与组织架构中差不多，但这这次的输入规模更大。Import 接口不用查询父节点的提升变得更加显著。而 Delete 接口这次测试做的是整棵树的删除，看来大规模删除下递归劣势更大。

### 3.3 总结

尽管一开始考虑到不同场景的分布可能会让优化的结论不一样，但是经过测试结论基本相同，只是因为输入规模的不同可能带来的优化效果更佳明显。

## 4. 其他思考

- §2.1.2 提到了路径索引长度的限制，如果使用 UTF-8 编码（ 2 ~ 4 bytes 一个字符），MySQL 只能保证至少 768 个字符的存储，超过这个长度的插入 MySQL 会直接报错。所以这里需要额外的限制保证极端情况也能正常运行。（ MySQL 里可以使用前缀索引，但这样会影响索引的性能 ）。

- 本地测试访问数据库的 RTT 大概在 0.3ms，这与云厂商中同可用区的数据相近（比如 asia-east1, asia-east2）。但要是涉及同地域不同可用区，以 Google 提供的 [RTT 矩阵数据](https://console.cloud.google.com/net-intelligence/performance/global-dashboard?hl=zh-cn&project=weighty-forest-427613-b1&pageState=(%22performanceDashboardTraffic%22:(%22v%22:%22internal%22),%22performanceDashboardMetric%22:(%22v%22:%22latency%22),%22pdNetworkTierState%22:(%22n%22:%22NETWORK_TIER_UNSPECIFIED%22))) 来看，这个延迟可以到 20 - 30ms.这会让递归查库并且发送多条 SQL 实现产生明显的性能劣势。

这个文档写于我开始接手前人代码的时候，觉得代码仓库里满屏的数据库递归十分不可思议。同时它们的服务器 CPU 相对老旧，低效操作带来的影响会被放大 —— 界面上大量功能依赖树形结构的展示，卡顿十分明显。另外其实旧的代码本身存在一些逻辑问题没有解决：

- 文档中讨论的并发问题（比如先查后更新）其实在旧代码中并没有被考虑。
- §2.1.1 提到父节点的名称不能唯一确定一个路径，但是旧系统里这么做了，并且强制约束全局不能有同名的节点，限制较大。

所以决定重新设计与重构，为了对照也留下了实际的性能对比测试。不过也发现中间需要考虑的东西不少，现在也仍留下了一些 TODO 会在未来继续探索。

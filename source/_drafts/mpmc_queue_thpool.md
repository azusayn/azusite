## 1. 需求

在最基本的并发模型中，每一个系统线程会绑定在一个任务上。当进行 I/O 密集型任务时（比如等数据从 page cache 复制到内存中），系统线程会进入休眠态（TASK_INTERUPTIBLE/TASK_UNINTERUPTIBLE），等待数据复制的完成，导致并发性下降。

为了解决这一点，我们需要将线程解放出来去执行别的任务。这就需要解决两个问题：

## 2. 线程池的两种实现

假设我们有一堆需要完成的任务需要在多个线程之间分配，为了使任务能在多个线程中共享，我们需要引入共享的任务队列（Task Queue）。
多个线程访问队列需要额外的同步机制。常见的选择有互斥锁（Mutex）和原子操作（Atomic Operations）。

### 2.1 利用互斥锁进行同步

在这个实现里，初始状态下我们创建固定的线程。每个线程在各自的循环里面不断的获取互斥锁，检查队列是否有需要执行的任务，然后释放锁。

但是队列为空的时候，如果每个线程仍然在循环检查队列是否有任务，就会造成忙等（Busy Waiting）的资源浪费，无效占用 CPU 资源。所以这里我们引入新的并发原语 —— 条件等待（Condition Wait）。这个函数会先使线程进入阻塞（BLOCKING）状态，直到别的线程调用了 `cond_signal` 或者 `cond_broadcast`

在阻塞期间，线程的上下文（寄存器中的数据，包括当前执行栈指针，TODO：还有什么来着）被保存在线程栈中，不会对 CPU 造成浪费。当被信号唤醒的时候，线程会进入就绪（READY）状态。等待 CPU 分配时间片后继续执行任务。

### 原子锁与互斥锁

- 同时在原来的数据结构中，我们使用一个 mutex 对整个数据结构进行了保护。读写操作都需要锁竞争。
mutex 竞争会导致极大的开销（TODO: 见 §）

为了避免使用 mutex， 我们引入原子锁的思路。

当两个 worker 需要并发修改变量的时候，如果变量的更新需要保持一致性（TODO： 或者叫做一定的逻辑？怎么表达）。以两个 worker 并发修改某个内存变量的值加一为例，如果不使用锁保护，就有可能某个
时间序列（TODO：是这个说法吗，看看数据库系统概念）下，两个 worker 同时读取到了内存值，然后同时在自己的工作区对这个值加 1，最后同时更新回内存位置，就会导致原本应该叠加的更新互相覆盖。
（这个是不是就叫 Lost Update），也就是 TOCOU 问题（time to check, time to use） —— 检查变量到使用变量之间有一个窗口，或者说，这执行两个操作不是原子的。

使用 mutex 进行保护的时候，worker 之间都要进行锁争夺，拿到锁的 worker 才能检查并更新内存值 (原子化)，这就解决了 TOCTOU 问题（TODO: 还有别的问题吗）。

而在使用原子锁的时候，针对需要更新的内存值，每一个 worker 会先保存一个旧值，在更新的时候检查内存中的值是否与保存的值一致，如果一致则成功更新，不一致则失败。使用 CPU 支持的原子指令（比如 TODO：）可以保证检查与更新的动作是原子的一条指令，不会有 TOCTOU 问题。同时使用互斥锁范式下，抢不到锁的 worker 会阻塞浪费很多 CPU 周期（TODO）。而在原子锁范式（范式这个词对吗）下，失败的 worker 只会在程序层面上返回一个失败值，然后由开发者决定何时重试（比如直接放在一个 while 中，也就是 spinning lock 自旋锁）。这就避免了阻塞带来的开销。

具体实现上，我们可以利用 C++ 包装的跨平台函数：

```c++
    // #include <atomic>
    bool compare_exchange_weak(int &__e, int __d, memory_order __m = memory_order_seq_cst) noexcept
    bool compare_exchange_strong(int &__e, int __d, memory_order __m = memory_order_seq_cst) noexcept
```

其中 compare_exchange_strong 是 compare_exchange_weak 的包装版本，他内部调用 compare_exchange_weak 自旋直到成功为止，用起来比较直观。
而内存序 （memory_order）一般使用默认即可，在 TODO: § 讨论这个参数

在 Golang 里，标准库限制了开发者能使用的原子调用的参数。比如一般只会使用 `CompareAndSwapXxx` 这样的函数，它相当于使用 `compare_exchange_strong` 搭配
`memory_order_seq_cst` 内存序。牺牲了控制粒度，但是写起来更加直观。

### mutex 耗时的原因， 唤醒与睡眠

mutex 竞争会导致没有抢到锁的线程陷入阻塞状态（由于用户态无法直接修改线程状态，需要 futex 这样的系统调用进入内核态），接着在修改线程状态的时候，
内核代码需要继续获取运行队列（run queue？ TODO：linux 线程队列什么样的来着），的锁，然后把线程从 run queue 中挪到睡眠队列去。

寄存器上下文需要存入栈中，唤醒的时候需要从进程栈中恢复。
